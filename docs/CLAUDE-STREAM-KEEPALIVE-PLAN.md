# 长工具生成期间的客户端断线修复

## 事实与目标

真实工程任务run-53e6ba1ed2c44c65a4d0e65b5aa2024a，原上游请求约251秒仍在途时Claude客户端重试，随后原连接在client_write断开。当前Chat适配器把工具参数累积到完整JSON再交给Claude，长工具生成期间没有向客户端发送内容。不能靠允许在途重复提交来修复，也不把本地心跳当作模型进展或计费token。

## 方案

对已校验的流式请求尽早返回SSE头，在等待上游连接、token或完整工具JSON期间发送标准ping事件。每个请求最多一个本地心跳线程，写入锁使整个SSE事件原子写出。Anthropic原生透传按完整事件发送，避免ping插入event和data行之间。message_stop和error前结束心跳；所有退出路径停止线程。非流式HTTP行为保持现有实现；已开始SSE的上游错误通过error事件报告，不能冒充message_stop。

独立心跳间隔参数用于传输和测试，不限制模型访问次数，也不产生模型请求。保留用户配置的上游超时与原请求追踪，错误和未知账务不重放。终态后不再发送ping，不能造成下一轮和旧响应串线。

## 对抗验收

真实本地HTTP上游模拟延迟响应头、工具参数中途停顿与原生Messages拆分事件；客户端较短的读取超时仍应拿到ping及最终正确结果。上游错误必须error且没有message_stop，同一失败不再请求供应商。断开客户端检查线程结束和状态记录。已有请求配对、模型固定、usage、顺序工具块和在途去重测试继续通过。修复载入前确认当前无活动Agent，正常重载本地服务后通过同一逻辑任务恢复真实工程工作，保留原失败尝试与费用未知。

审查结论：修的是流式连接主路径，局部标准ping不能保证所有网络故障恢复，但能消除已观察到的无数据等待。不得把心跳展示为AI思考进度，或因此放松重复计费保护。
