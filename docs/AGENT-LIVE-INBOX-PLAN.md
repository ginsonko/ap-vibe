# 运行中伙伴消息的可靠递送

## 目标和现场依据

工程对照的独立检查在运行中收到初始 SHA 基线入口。当前服务保存消息、显示气泡，但只有启动时自动提供消息；模型若没有再次主动查询，会错过后来发送的帮助。需要在正常工具返回时递送当前任务的新消息，让交流成为实际上下文。服务保存、递送给执行器、模型采用必须分开说明。

## 实现方案

复用现有 collaboration 消息表，增加按当前 run、逻辑任务、明确接续来源以及实际收件人查询的增量收件箱。以数据库递增序号分页，不按时间戳去重，不删除历史，不跨任务自动投递无归属广播。公开只读接口允许任何客户端按需查询，模型不用先绑定项目。

托管 MCP 在工具正常返回后附带本运行新增工作消息。运行身份由执行器环境传入，不能由工具参数改变；游标在本 MCP 进程保存，失败不前移，重启允许重复递送而不漏消息。消息有真实发送者、归属和 ID，并明确属于参考数据。一次有界查询失败不影响原工具结果，不启动服务或等待模型，不为读取新增额外模型调用。

双方执行器提示和 Skill 统一说明：MCP 返回可带入新消息；连续使用本地文件/命令工具时在自然阶段和最终交付前调用收件箱。Claude 原生工具是否需要 PostToolUse 扩展，要先实测当前 MCP 路径再决定；此切片不承诺打断正在等待上游的模型或即时唤醒已退出会话。

顺便修正消息气泡的归属：逻辑任务发信应显示在当前相关运行；广播不能因为带任意 task_id 就显示在该伙伴所有历史任务上。气泡是已保存的交流活动，不等于已读或采用。

## 对抗审查

- 并行收件人和多任务不能串线；关联逻辑任务与明确交接仍可读取。历史消息目录仍完整可查。
- 超过一页的新消息按序翻页不能被后来的消息挤掉；同时间消息不丢。身份变更不能复用旧游标。
- 服务重启/网络失败只影响附带消息，不得把成功写档案结果变成失败并引发重复提交。
- MCP 原有工具结构与 isError 保留；追加内容不能伪装成用户/系统指令，不能扩大当前任务授权。
- 不把递送当采用；真实短任务须在启动后收到新事实，并在实际成果中使用，方能标记采用路径通过。
- 发布、全部自动维护和长期收益仍单独验收，不能由这项检查推出全部完成。

## 验收与恢复

实际页面截图 01-before.png 显示发信入口埋在全部历史消息之后，多选框还需使用特殊键。修订界面方案：顶部提供“给任务补充信息”，选择任务自动确定收件伙伴，活跃任务排在前面；结束任务提示消息留待接续，不暗中启动模型。普通多人留言保留在展开区，清楚说明不会自动进入无关新任务。历史消息放入有限高度的滚动区域。所有发送保留内容与稳定请求编号，响应丢失后重试不能重复保存。

先测试增量、分页、任务/收件人隔离、广播/逻辑任务事件、重启重读和失败后恢复；真实 stdio MCP 子进程验证。全部伙伴空闲时正常重载，然后一个有界真实托管任务只消费运行后发送的新事实，读取文件确认采用且无不相关消息。保存原请求和结果，结果未知不重复提交。同步 Skill 的说明，增量写档案并回读。
