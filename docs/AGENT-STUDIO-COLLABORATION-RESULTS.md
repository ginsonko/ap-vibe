# Agent 工作室：协作运行与验收记录

更新日期：2026-09-09。本页区分运行器能力、真实模型任务表现和仍未完成的产品体验。

## 现在能做什么

给任务选择一个或多个上游。任务先进入“等待上游成果”，所有上游正常返回后自动开始；启动器在成果目录生成 `ap-vibe-dependency.json`，包含来源任务、伙伴身份、原目标和真实文件入口。伙伴可以按需读文件并继续工作，也可以承担独立验收。

前端可多选上游、查看上下游任务、取消等待、安排伙伴核验；协作看板展示中文伙伴名称、工作消息、交接顺序和原任务入口。消息通过 MCP 发送并持久化，使用相同请求编号重试不会重复保存。相同编号换内容会得到明确冲突。

这不是把原始会话全部塞给下一个模型。启动时只提供相关消息和成果目录，更多任务公开输出通过工具按需读取；私有推理不进入公开事件。

## 已有真实证据

串行案例 r4：三个真实 Claude Code 会话使用配置的 Grok 模型，分别写原始文件、读取原文并写核验文件、读取两级成果并独立对照。下游和验收会话都先等待，再自动启动；实际 MCP 工作消息、Write/Read、执行器成功结果和磁盘文件均可回读。父会话另行读取三份文件并记录 SHA256。

并行案例 r5：Grok 写新手说明，Gemini 写排障说明。二者同时执行，验收伙伴等两者全部返回后读取真实文件。验收指出排障文案错误地引入了验收前置条件；原作者收到具体意见后接续修改，再由原验收会话等待并复查。最后结果以对应验收收据为准。

这些案例证明特定文档任务的跨模型衔接；不能据此声称所有模型都可靠，或复杂工程必然更快、更便宜。

本机证据入口（不会随发布包含私人运行数据）：`.local-acceptance/coordination-r4.json`、`coordination-r5.json`、`coordination-r5-correction.json`、`real-r4-artifacts/`、`real-r5-artifacts/`。

## 自动启动的语义

- `waiting`：已登记，尚未提交模型请求。
- `starting/running`：准备或执行当前任务。
- `awaiting_review`：执行器正常返回；可以供下游使用，内容仍需验收。
- `completed`：有明确验收记录。
- `failed/uncertain/interrupted`：未完成或结果不确定；后续等待不会误判成功，原请求不自动重放。

晚登记的任务会立即检查已经完成的上游。状态转换在短数据库事务内提交，随后启动进程；并发扫描用条件更新避免重复唤醒。服务循环补查等待队列，覆盖完成提交与唤醒之间发生重启的情况。已启动但被中断的任务不会因为服务重启重新付费执行。

依赖表中的 `completed` 表示上游已返回，与任务的人工或代理验收记录不同。工具返回解释和任务状态，避免把调度就绪当作内容通过。

## 可调用入口

`POST /v1/ap-vibe/agents/start` 沿用已有角色和项目，`depends_on` 可省略、填写一个 run_id，或填写多个 run_id 的数组。不同任务保持独立成果目录；同一会话接续保持原目录与历史。

`ap_vibe_collaboration_list({})` 返回任务目录与消息；指定 `run_id` 可查看该任务的公开输出。`ap_vibe_collaboration_send` 使用稳定 `request_id`、接收伙伴 `recipient`、关联任务 `task_id` 和正文；托管执行器提供真实发送者身份。

现有失败交接 API 保留接手记录、原结果和任务归属。它尚不代表接手模型已自动完成修复。

## 已修复的异常

文本与工具混合响应原先会交叠开启内容块，现按 Claude 流式协议先关闭前一块再开启下一块，并有回归验证。网络中断也区分上游读/连接与客户端写，便于定位原因；不将协议修正等同于消除全部供应商网络故障。

等待取消不提交模型请求。未知上游和跨项目依赖会指出具体问题。等待期间配置或项目无法恢复时保留失败原因，不能悄悄更换模型身份。

本次内置浏览器初始化报“failed to write kernel assets”，重置后仍失败。构建与接口验证不替代页面逐按钮验收；新版多选依赖、协作看板和移动端视觉验收暂未完成。公开发布、干净安装和宣传交付依然需要完成各自的真实验收。
