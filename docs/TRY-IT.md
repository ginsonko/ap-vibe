# 第一次内测，试这几个真实场景

不用一次测试全部功能。先用一个自己的小型长期项目，避免一开始就让多个模型修改重要业务。

## 1. 安装后能找到工作台

把 README 的安装口令交给 Codex。预期它读取安装说明、完成本地安装，并返回实际地址。页面能打开，左侧显示服务在线。默认端口占用时地址可以变化，不应抢占其他程序。

还没安装 Python 或网络无法访问 GitHub 时，应得到明确原因和下一步；不能把只下载源码说成安装完成。

## 2. 不懂 Skill 名字，也能开始

对 Codex 说：“我要长期维护一个离线阅读记录工具，先设计数据结构，暂时不写应用。”

预期它正常执行你的需求；能读取项目目录，依据真实工作归类或创建项目。到“项目与记忆”查看简介、目标、设计和待办。档案应明确“目前只有设计”，不能虚构已经实现的功能。

## 3. 新会话接手同一项目

新开任务，进入同一个业务目录，说：“继续阅读记录工具，先读已有设计，补充重复书名的处理规则。”

预期复用原项目，保留以前的决定，记录新增规则。询问“用了什么已有资料”，应给出实际读取和采用的内容，没证明收益时直接说明。

## 4. 手工改过的内容还在

在章节里“修改这一章”，添加一句明确的用户约束。再让原任务做一次小修改，结束后回看：人工内容、旧决定和事故仍保留。若任务报告写入超时，先按请求编号查询原结果，不重复覆盖。

## 5. 看消息时不被打断

首页点击任务标题，在会话页向上翻历史。原任务产生新消息时，应保留阅读位置。点击回到最新，再有新消息时应自动跟随。Markdown、代码和表格应可阅读。

## 6. 值得拆分的任务与独立验收

在伙伴与配置中添加推荐模板、填写连接并开启自动协作。照常提出一个确实值得拆分的需求，例如“改善这个个人网站的首页，保留功能，并检查手机显示和表单”。先观察普通需求是否自然分工，不在第一句话要求调用某个工具。几分钟的小改动直接完成也是正确行为。

预期管理员根据可用伙伴安排，下游等待依赖，满足后启动；验收读取真实成果。未通过有具体理由和返工记录，完成后返回原任务。看到“运行完成”或角色动画不能单独代表验收通过。若自然需求未分工，再明确要求工作室委托用于诊断；请分别记录两次结果。

## 7. 服务恢复与资料导出

先通过正常停止入口停掉自己的 AP-Vibe，再双击桌面启动器。预期恢复同一个数据目录和项目，打开实际地址。

导出项目包时检查预览。它含当前档案和有界历史，不是代码或密钥备份；导入另一套工作台创建独立副本，不覆盖原项目。

## 8. AP 教师保持可选

保持 AP 教师关闭，仍可用监看、档案和按需恢复。开启时应说明发送到哪个外部服务、需要网络与费用。关闭后不再为新的教师工作发起请求；已有请求按其原状态处理。

## 怎样给出有用反馈

在 GitHub Issues 写明：想完成什么、第一步和第二步做了什么、希望发生什么、实际发生什么、Codex/Claude 版本和 AP-Vibe 版本。附脱敏截图或最小复现材料即可。

不要上传 Key、Cookie、完整会话、私钥、数据库或私人项目资料。另一实体机器、真实 Windows 整机重启和长期质量变化尤其欢迎反馈；这些仍需要持续内测。
