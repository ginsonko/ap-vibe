方式：编写者按失败场景进行文档自审，随后将修正合入主设计。这不是独立第三方审计，也不是实现验收；所有新增运行能力仍须真实实验。没有为尚未实现的功能打成熟度分数。

## 1. 审查结论

方向可进入基础实验阶段。现有项目档案、消息队列、版本和恢复基础使它适合在 AP-Vibe 上增量构建。当前不能直接进入“任意模型通用团队”的宣传或大规模UI施工，关键前提是 Claude 与目标服务的工具协议、托管会话控制和 Codex 唤醒回读。

自审没有发现修订稿中必须通过新增用户审批才能解决的问题。可靠投递、稳定身份和外部结果对账是自动执行的必要机制，不应成为普通查询的额外门槛。后续必要依赖失败时修复第一断点，不围绕失败堆“请核对/请确认”按钮。

## 3. 对几个核心想法的重新判断

### “只填 URL、Key、模型就可以”

可以作为用户界面目标。工程必须在后面完成协议识别、能力回读、配置隔离和失败恢复。不能把这三个字段转成环境变量后就宣称任意模型可用。推荐先验证一个目标第三方模型的完整工具链，再扩大目录。

### “谁空闲谁主动帮忙，谁慢就换掉”

主动认领独立待办有价值。仅凭等待时间或其它 Agent 的主观判断换掉 owner 不可靠；不同任务难度和工具等待无法直接比较。改为有状态的求助/拆分/交接，先收集checkpoint，再转移所有权。执行中的外部副作用要查结果；没有输出时其它人仍可认领无依赖工作。

### “全员互相看到能形成会议”

按需可见有价值，默认全量广播会增加成本、泄露无关上下文并让错误互相传播。目录和公开摘要开放，定向消息触发行动，会议按话题聚合。争议记录可查，负责人做有证据的决定，不能不断投票代替运行验收。

### “让 Codex 规划完就停，最后再唤醒”

这是降低无效等待的正确方向。难点是已经派发但回执丢失、接收方忙、依赖动态变化和重启后的通知去重。必须由本地持久订阅和队列承担，不能靠一个模型持续醒着问另一个模型是否完成。

### “多个便宜模型一定比一个强模型划算”

不成立为先验保证。小任务和强串行任务很可能更慢；低质量初稿造成强模型大改也可能更贵。按任务类别做同题对照，保留失败、订阅用量和返工，再决定哪些适合自动拆分。产品应允许一人完成，而不是强行团队化。

### “Skills保证每次收尾都维护完档案”

纯提示无法保证。托管任务可以检查具体维护收据并做有界补偿；普通外部终端只能使用其真实支持的hook/MCP，不应承诺无法实施的强制控制。主体成果和档案同步分别显示状态，不能为补齐字段无限占用用户额度。

### “AP开启就会越来越聪明”

目前只能作为需检验的研究假设。AP可以提供跨任务建议和反馈学习入口，但必须证明使用的是既有认知对象、学习不是界面数值变化，并测净收益。关闭教师时完整基础协作可用；实验无收益时应诚实报告。

## 4. 必须由实验回答的未知

1. 当前银子API目标模型的Messages兼容、工具调用、多模态、压缩/恢复及辅助模型路由。
2. Claude 2.1.215的流式输入确认、既有交互会话公开事件覆盖和外部可控边界；后续CLI升级可能改变行为。
3. Codex当前安装组合在空闲、忙碌、退出和重启时的原会话唤醒与回读语义。
4. 多个真实模型/CLI并发时的总延迟、返工和费用；单机CPU、内存和磁盘事件增长。
5. AP原生协作事件映射、长期学习泛化、额外费用与净收益。
6. 像素地图是否比普通列表更易理解；素材帧间一致性和无动画模式是否同样易用。
7. 首次安装、目录/账号权限、端口退避、第三方CLI条款与公开内测支持组合。

这些未知已各自映射到实验，不能以“文档逻辑看起来没问题”直接消除。实验结果会修改能力表和阶段范围；不为了保持最初设想而隐瞒不兼容。
